# 0003 — SSRF control and its known gap

Date: 2026-08-22
Stage: 2 — Identity and bookmark API
Status: accepted

## Context

D1 put article fetching on the backend, so the pipeline issues server-side HTTP requests to
whatever URL a client submits. That is textbook SSRF: the VPS can reach its own loopback, the
Docker network, the Postgres port, and — on most hosts — a cloud metadata endpoint at
`169.254.169.254` that hands out credentials to anything that asks.

PRD §7 lists "Input URL validation" under Security without saying what it must reject.

## Decision

`bookmark/UrlValidator` rejects, before any fetch:

- schemes other than `http`/`https` (blocks `file:`, `gopher:`, `jar:`)
- embedded credentials (`http://user:pass@host/`)
- relative or malformed URLs, and anything over 2048 characters
- any host where **any** resolved address is loopback, any-local, link-local, site-local,
  multicast, IPv6 unique-local (`fc00::/7`), or carrier-grade NAT (`100.64.0.0/10`)

DNS resolution sits behind a `HostResolver` interface rather than calling
`InetAddress.getAllByName` directly.

## Alternatives

**Checking only the first resolved address.** A hostname can return several A records. An
attacker controlling DNS returns one public address and one internal one; checking only the
first passes validation while the HTTP client may connect to either. All records are checked.

**A domain allowlist.** Airtight, and useless — the product's entire premise is fetching
arbitrary articles.

**Calling `InetAddress` directly from the validator.** This is what was written first, and
its test suite failed on a hostname that simply did not resolve. That exposed the real
problem: the validator's tests were doing live DNS, which violates the no-network rule in
`docs/CODING_STANDARDS.md`, made the suite dependent on the machine's resolver, and made the
multi-record attack above **untestable** — real DNS cannot be made to return a chosen pair of
addresses on demand. The `HostResolver` seam fixes all three. The suite now runs 22 cases
offline in ~40ms, including the mixed public/private case.

## Consequences

**This does not close DNS rebinding.** We validate a hostname's addresses, then hand the
*hostname* to the HTTP client, which resolves it again. A hostile resolver can return a public
address to the validator and a private one to the fetcher, with a TTL short enough to flip in
between. Closing it properly means resolving once, pinning the resulting IP, and connecting
to that IP with the original `Host` header. That belongs in stage 4 with `ArticleFetcher`,
where the connection is actually made — **the validator alone must not be treated as
sufficient protection.**

Related, and also stage 4's problem: this validates the submitted URL only. A redirect chain
can end anywhere, so every hop must be re-validated. Recorded in `CLAUDE.md`.

Two lesser consequences:

- Hosts that fail to resolve are rejected outright, so a transient DNS failure surfaces as a
  400 rather than a retry. Acceptable — the user can resubmit — but it means DNS flakiness
  looks like a bad URL to the client.
- Rejecting site-local addresses means ReadCast cannot summarise anything on a private
  network. That is the intent, but it will confuse anyone testing against a LAN server.

## Also decided

`X-Device-Id` must parse as a UUID, not just be non-blank. It is stored lowercased and
canonical. A free-form string would let clients fill the `users` table with arbitrary keys,
and PRD open question #2 already framed identity as a device UUID.
