# 0024 — Summaries explained through a listener's lens

Date: 2026-09-30
Stage: beyond the plan — new feature (`docs/LENS_PLAN.md`, stages L1–L4)
Status: accepted

## Context

A new capability the PRD does not have: a listener saves a short description of themselves
once, and summaries are explained in their terms. Not a different summary — the same coverage,
with unfamiliar terms explained, a comparison from their world where one genuinely fits, and,
only when the article bears on their work, a closing "For a …" sentence. Nothing may be added
that the article does not say. This diverges from the PRD, which has one summary per article
and no user profile.

The design came out of a staged experiment (`docs/experiments/lens/`: three articles chosen to
test coverage, explanation and restraint — Fowler's *Circuit Breaker*, Paul Graham's *Do Things
That Don't Scale*, Wikipedia's *Offside* — against four profiles, one of them a prompt-injection
attempt). What each round showed:

| Round | Shape | Result |
|---|---|---|
| v1 | one prompt, profile inside it | explains well; forces takeaways and analogies onto *Offside* ("arms are like decorative UI elements") |
| v2 | same, with rules ranked and analogies capped | forcing gone, but so is most of the explaining — it overcorrected |
| v3 | **two calls**: a brief, then the narration | explanation back and specific; takeaways right; profile never reaches the narration |
| model comparison | v3 on five models, 12 cases each | see Alternatives |
| L4 ×3 | the shipped prompts on Nemotron | below |

One prompt asked to compress, keep coverage, explain for one person and judge relevance kept
trading one of those for another. Splitting the judgement from the writing fixed both.

## Decision

**Two model calls per lensed summary.** `ListenerBriefService` sends the profile and the
article and gets back JSON: up to five terms to explain (at most two with a comparison) and a
takeaway or null. The narration prompt receives only a notes block built from that — never the
profile. The takeaway is appended by code after tightening and truncation, and its words are
reserved from `SummaryTarget` first, so it is never the part cut.

**Deterministic where the model was not.**
- Comparisons: the prompt says two, and after softer wording produced three to five per brief,
  `notesFor` keeps only the first two regardless.
- Takeaway openings: the prompt says "name only their kind of work", and the model still wrote
  "For a backend engineer building payment services". `ListenerBrief` cuts a short opening back
  at the first qualifier ("building", "on", "who", …).

**A lens never fails a bookmark.** A brief that cannot be had after one retry leaves a plain
summary, `lensApplied = false`. Reuse keeps the two apart: lensed bookmarks reuse only a summary
made for the same profile *whose brief succeeded*; plain ones only plain summaries.

**The profile** (`listener_profiles`, 50–1,500 chars) is written by the listener's own
assistant from a prompt we serve, screened once on save by one model call (`ok` / `instructions`
/ `abusive` / `not_a_description`, outside any transaction, 503 rather than a skipped check when
it fails), and copied onto each bookmark at creation so later edits never change a bookmark in
flight. It stays on the bookmark after summarising, for a future "listen again as…".

**Stay on Nemotron 3 Ultra.** Measured with both calls, $0.020 per lensed summary.

Measured on the shipped prompts, three runs:

| | Result |
|---|---|
| Takeaway where one should never appear (*Offside*, unrelated articles) | **0 of 24** |
| Takeaway on the clear cases (designer and engineer on *Circuit Breaker*, marketing on the startup essay) | 2 of 3 each |
| Comparisons per brief, after the cap | ≤ 2 in every case |
| Engineer's *Offside* (profile no longer says "never followed sports") | football terms still explained from the role alone |
| Injection profile | ignored in every output; used only as the role "marketing manager" |

## Alternatives

**One prompt with the profile in it (v1/v2).** Cheaper by a call, and it failed in both
directions — see Context.

**A stronger or different model.** Compared on v3, 12 cases each:

| Model | $/summary | Note |
|---|---|---|
| Nemotron 3 Ultra | 0.020 | shortest sentences; over-respells some names |
| Gemini 3.8 Flash | 0.034 | clearest prose; the fallback if quality needs to move |
| DeepSeek V4 Pro | 0.035 | reasons 5–17k tokens; echoed the profile |
| Kimi K2.6 | 0.054 | best explanations for a newcomer; reasons 11–22k tokens, slowest |
| Claude Sonnet 5 | 0.059 | best at names and acronyms; sentences too long for the ear (25.5 words avg) |

None was better enough on this task to justify the cost; the two-call shape mattered more than
the model.

**Presets instead of free text.** Easier to cache and test, and it throws away the part that
makes this work — the listener's own assistant already knows them. Free text, with the save-time
check, won.

**"What I'm new to" in the profile.** Dropped at the owner's request as too personal. The brief
now infers gaps from the role and what the listener knows well; the engineer's *Offside* showed
that is enough.

**Tightening the respelling rule.** The flagged respellings ("Virgil van Dyke", "Sah-kee") looked
wrong on the page. `/dev/phonemize` showed they were right: plain "van Dijk" is read "van Dake",
plain "Sacchi" "Sack-eye". The rule stays.

## Consequences

- A lensed summary costs a second model call and cannot share a cache entry with plain or
  differently-profiled summaries of the same article.
- The takeaway rule is judged on samples of three. It favours missing a fair takeaway over
  forcing one; the designer on *Do Things That Don't Scale* never gets one.
- The two deterministic fixes are heuristics: the qualifier list in `ListenerBrief` can miss a
  phrasing, and the comparison cap keeps the first two, not necessarily the best two.
- The profile is personal text stored on every lensed bookmark. Deleting the profile does not
  remove those copies.
- Respelled names ("van Dyke") now reach more readers, since lensed summaries are more likely to
  be read as well as heard. 0011's split between display text and narration text is the fix,
  still not built.
- `docs/experiments/lens/` holds the harness and prompts; re-run `run_prod.py` after any change
  to the brief or narration prompts.
